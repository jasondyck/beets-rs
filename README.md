# beets-rs

A Rust port of the core of [beets](https://github.com/beetbox/beets), the music
library manager: import with MusicBrainz autotagging, a SQLite library, beets'
query language and path-format templates.

The binary is `beet`, and the query, template and config syntax follow beets,
so the [beets docs](https://beets.readthedocs.io/) mostly apply. The library
database has beets 2.14's schema, but config and library live in
`~/.config/beets-rs/` (override with `$BEETSRSDIR`) so a real beets
`library.db` is never touched; `beet migrate-beets` copies one in (see below).

```sh
cargo build --release
beet import ~/Downloads/SomeAlbum        # interactive autotagging
beet import -q -m ~/incoming             # quiet: apply strong matches, skip the rest
beet import -i ~/Downloads               # incremental: skip folders imported before
beet ls artist:radiohead year:2000..2009 year-
beet ls -a -f '$albumartist - $album ($year)'
beet modify -a 'in rainbows' genre=Alternative
beet modify nude 'title=$title (live)' mood=calm   # values are templates; unknown fields become flexible attributes
beet mv -e -d /mnt/usb artist:radiohead            # export copies with library path formats (library unchanged)
beet update -F title -F artist                      # re-read changed tags (only these fields), drop deleted files
```

## Differential testing

`tools/diffbeets/diffbeets.py` builds the same library with reference beets
and with beets-rs (generated audio, same config) and compares `ls`, `ls -a`,
`-f` templates and `mv -p` destinations over ~1000 cases taken from beets' own
tests, runs the same cases on a beets-rs library made with `migrate-beets` from
reference beets' library, then has each tool write its tags and compares the
files as MediaFile reads them (and both tools' reading of the files beets
wrote), and runs import, fetchart and embedart scenarios on fresh libraries
(art phase: generated images, a local server for downloads); known,
deliberate differences are listed with their reasons in
`tools/diffbeets/cases/`. See `tools/diffbeets/README.md`.

## Adding a plugin

A plugin registers itself from its own file (see any file under `src/plugins/`)
with an `inventory::submit!` of `crate::plugin_registry::PluginDef`, so adding
one touches only its own new files, a README row and its diffbeets cases.
`build.rs` scans `src/plugins/` and generates the module list in
`$OUT_DIR/plugin_modules.rs` (included by `plugins/mod.rs`, with absolute
`#[path]`s), so a new file (or `name/mod.rs` directory) is compiled without
editing any central list:

```rust
inventory::submit! {
    crate::plugin_registry::PluginDef {
        name: "myplugin",            // `plugins:` name
        order: 100,                  // order in beets' bundled-plugin list
        defaults: r#"myplugin:
    setting: 1
"#,                                  // settings the plugin's __init__ adds
        config_keys: &["myplugin"],  // top-level keys of those defaults
        redacted: &[],               // dotted keys `beet config` hides
        make: Some(registry_make),   // the plugin constructor
        fatal: false,                // a setup error ends the command
        commands: &[crate::plugin_registry::PluginCommand {
            order: 100,              // position in `beet --help`
            plugin: "myplugin",      // the plugin the command checks/enables
            build: build_mycommand,  // fn() -> clap::Command
            run: run_mycommand,      // fn(&Config, &Library, &[Box<dyn Plugin>], &ArgMatches)
        }],
    }
}
```

`order` in `PluginDef` is the plugin's position in beets' bundled-plugin
list (it orders the "available:" names and the walk over enabled plugins);
`PluginCommand.order` is the command's position among the plugin commands in
`beet --help` (core commands come first, `version`/`help`/`config` last).
Both are plain numbers picked per plugin: leave gaps between them (e.g. ten
apart), take the next one for a new plugin, and the registry's tests fail on a
duplicate (`plugin_orders_are_unique` / `command_orders_are_unique`). Ties
would otherwise depend on link order.

`plugins::load`, the configuration defaults (`beet config -d`) and the plugin
subcommands on `beet`'s command line are built from this registry; the core
commands stay in `main.rs`. A plugin command takes the same clap arguments it
would in beets (derive `clap::Args` and `augment_args` on a `Command`), and
`run` does the work. Add tests next to the plugin (`src/plugins/..._tests.rs`,
`mod tests` at the bottom), a README table row (the table is sorted
alphabetically), and its cases as a module under `tools/diffbeets/cases/`
(auto-discovered; definitions such as `CASES`, `ART_CASES`, `IMPORT_CASES`,
`EXPECTED` and `ORDER` are picked up).

## Layout

`model` (typed fields + flex attrs) · `library` (SQLite, beets' schema and migrations) · `migrate` (`migrate-beets`) · `query` · `template` ·
`paths` · `duplicates` (duplicate keys, Upgrade, prompt summaries) · `fileops` (copy/move/link/reflink, pruning, ignore globs) · `media` (reading/writing items' files, art) · `mediafile` (port of MediaFile's tag mapping) · `props` (mutagen's length and bitrate) · `mb` (MusicBrainz) · `autotag` · `importer` ·
`artresizer` (image operations) · `commands` · `diff` (change highlighting) · `logging` (`-v`) · `events` (the plugin event bus) · `state` (import resume/history) · `ui` · `plugins/` (`fetchart`, `embedart`, `art` (embedding helpers), `lyrics`, `lastgenre`, `requests` (HTTP session)).
